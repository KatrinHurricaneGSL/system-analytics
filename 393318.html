Поле snapshot_json содержит сохраненные сведения об организации, проекте, шаблоне, ответственном, бюджете, этапах, нормативных ссылках и маршруте согласования.

Новая версия создается при создании и изменении устава, отправке на согласование и принятии решения согласующим. Добавление комментариев и создание проекта из устава не увеличивают номер версии.

Поле hasSnapshot в API показывает наличие непустых данных в snapshot_json.

Связи и особенности хранения

  1. Устав связан с организацией и может содержать ссылки на проект и шаблон. Автор, ответственный и согласующие связаны с таблицей accounts, нормативные ссылки с таблицей regulatory_documents.

  1. При удалении устава система каскадно удаляет его дочерние записи. Отдельный метод удаления устава в API отсутствует. При удалении проекта или шаблона ссылка в уставе получает значение NULL. Удаление организации приводит к каскадному удалению связанных уставов.

  1. При изменении устава система полностью заменяет статьи бюджета, этапы, нормативные ссылки и шаги согласования. Идентификаторы прежних записей не сохраняются, история изменений остается в таблицах версий и журнала событий.

  1. Максимальная длина текстовых полей ограничена на уровне БД, но API проверяет не все ограничения. Например, текст комментария может содержать до 4000 символов, а его копия в журнале до 2000. Превышение длины записи журнала может привести к ошибке сохранения.

  1. Для полей charter_id и version таблицы истории версий создан составной индекс, но уникальность пары не установлена. Защита от одновременного изменения устава не реализована.

  1. В сохраненных данных встречается прежнее значение статуса in_approval, которое отсутствует в текущем перечне допустимых статусов.
